# AI Energy Life Assistant · AI 协作方法论

> 本文档记录在本产品设计项目中 AI 的实际参与方式、人工判断、事实核验与方案修正过程。
> 核心主张：**AI 用于加速候选方案生成与结构表达，最终的产品判断、风险取舍与责任始终由人承担。**

---

## 1. 使用目的与边界

本项目使用 AI 的目的不是让 AI 代替产品经理做最终决策，而是：

1. 把开放问题拆成产品定位、用户场景、信息架构、核心流程、价值量化、商业化与技术可行性等模块。
2. 快速形成候选方案，再通过人工质疑击穿未经验证的假设。
3. 对容易记错的竞品能力进行官方资料核验。
4. 把「AI 很智能」改写为可计算、可解释、可验证的省钱闭环。
5. 沉淀可供原型、研发评审、用户研究和商业验证继续使用的结构化材料。

AI 未被授权、也未实际完成以下事项：访问任何真实用户数据；连接生产系统或未公开接口；训练或上线真实预测模型；开展广告投放、真实用户访谈、A/B 测试或财务审计。

## 2. 实际使用的工具与能力

| 能力类别 | 实际用途 | 产出 | 局限 |
|---|---|---|---|
| 对话式 AI 推理与写作 | 拆解问题、生成候选框架、补充流程与指标、回应质疑并改写方案 | 产品策略、场景分析、流程、量化模型、商业验证 | 可能生成听起来合理但未经证实的数字，需人工审查 |
| 结构化分析 | 用表格、优先级、公式、分层用户体系与决策门槛组织信息 | P0/P1/P2、分层能力、ROI 公式、验证指标 | 优先级和阈值属于产品判断，不是客观事实 |
| 公开网页检索与阅读 | 核验竞品能源能力与产品公开能力 | 官方链接、事实修正、风险识别 | 公开页面可能更新，登录后的内部文档无法确认 |
| 本地文件读写 | 生成产品方案、原型、方法论与系统报告 | 多份 Markdown / HTML | 只负责本地文件，不代表已通过业务 / 技术 / 法务评审 |

## 3. 迭代方法

产品设计遵循「生成候选 → 击穿假设 → 收敛修正」的循环，而不是一次性让 AI 输出终稿：

```
① 框架先行   → 定义问题、拆解协同与量化价值
② 场景深化   → 每个场景补齐痛点 / AI 价值 / 商业价值 / 差异化
③ 信息架构   → 建立 P0 / P1 / P2 功能结构
④ 核心流程   → 首次设置、日常优化、停电应急的端到端路径
⑤ 价值量化   → 反事实基线 + 三档口径
⑥ 事实核验   → 用官方资料修正绝对化竞品判断
⑦ 红队质疑   → 连续击穿「语音、游戏化、免费带货、用户基数」等假设
⑧ 商业化验证 → 先证伪再投入
⑨ 技术评估   → 分模块可行性、周期与风险
⑩ 整合交付   → 只纳入「采用 / 修正后采用」的结论
```

### 3.1 关键迭代记录（摘要）

| 主题 | AI 初始判断 | 人工质疑 / 核验 | 最终决策 |
|---|---|---|---|
| 语音定位 | 语音是核心差异化 | 能源查询低频，用户不常戴耳机 | 降为可选入口，推送 + 一键执行升 P0 |
| 游戏化 | 排行 + 积分提升留存 | 冷启动无样本，积分稀释真实省钱 | 删公开排行与线性积分，改个人目标 |
| 商业模式 | 免费 App 促进硬件销售 | 相关性 ≠ 因果增量 | 内嵌 MVP + 对照实验，只算增量贡献毛利 |
| 竞品判断 | 竞品没有能源 / 联动能力 | 官方资料显示竞品已有相关能力 | 差异化改为第一方闭环与结果验证深度 |
| 用户准入 | 只有储能用户才是有效用户 | 目标过窄，无储能用户流失 | 改为 L1/L2/L3 分层能力 |

## 4. 事实、推断与假设分级

为避免把 AI 的流畅表达误当作事实，本项目采用四级标记：

| 等级 | 定义 | 使用规则 |
|---|---|---|
| **F1 官方已核验事实** | 有当前可访问的一手官方页面支持 | 可写入事实陈述，保留链接与访问日期 |
| **F2 输入给定** | 来自题目或用户给定数字，尚未独立核验 | 写明「暂按……估算」，不能伪装成市场事实 |
| **I 分析推断 / 产品决策** | 基于事实做出的计算、优先级、架构判断 | 必须公开前提，不能写成既定承诺 |
| **H 待验证假设** | 需用户研究、真实数据或实验才能判断 | 必须绑定验证方法、通过门槛与停止条件 |

### 4.1 关键主张分级示例

| 主张 | 分级 | 处理方式 |
|---|---|---|
| 「每月可省 15%–30%」 | H | 只能作为试点目标或情景区间，不能作为无条件承诺 |
| 「70% 用户没有储能设备」 | H | 需用户分布数据验证 |
| 「欧美家庭月均电费 $150」 | F2/H | 示例值，需替换为目标市场权威数据 |
| 「竞品已有部分能源 / 联动能力」 | F1 | 已通过官方页面核验 |

## 5. 量化框架

### 5.1 省钱模型

```text
AI 净节省
= 峰谷移时收益 + 光伏自用增益 + 储能套利收益 + 减少耗电收益 + 需量费用收益
− 电池循环损耗 − AI 调度额外成本
```

核心约束：

1. 基线必须是「同样硬件、没有 AI 干预」的反事实成本，不能把硬件收益全部归给 AI。
2. 「已验证节省」只纳入真实执行且数据可信的事件；建议未执行时只能写「预计可省」。
3. 保守 / 中等 / 乐观分别对应较低分位、个性化中位与充分采纳后的潜力情景。
4. 光伏自用、储能套利与移峰收益必须去重。

### 5.2 ROI 模型

```text
增量贡献毛利 = 实验组相对对照组的硬件转化增量 × 单笔贡献毛利
               + 配件连带销售增量 + 可选服务毛利 + 可归因的成本下降
ROI =（增量贡献毛利 − 完整年度 TCO）÷ 完整年度 TCO
```

关键判断：不能把所有用户的硬件购买都归因给 App，也不能只用收入覆盖输入的成本；应计算因果增量并补齐完整 TCO。

## 6. 红队质疑方法

方案质量主要来自**主动击穿**，而非润色。规则：

> 质疑成立时直接改优先级、删功能或缩小产品范围，不为保持原方案完整而辩护。

高频追问清单：

1. 没有储能设备的用户为何使用？
2. 语音是否真比通知和触屏更高效？
3. 游戏化是否公平、能否冷启动、奖励成本由谁承担？
4. 产品带来的是否是增量贡献毛利？
5. 数据授权、跨团队接口、模型误差和安全责任能否承担？

---

## 7. 已知局限

1. AI 输出可能产生「合理但错误」的产品能力、市场数据与开发周期。
2. 题目给定的 70%、15%–30%、$150、$30 万等数字未在项目中独立证明。
3. 官方公开页面无法替代内部 API、固件、账号体系与合规审计。
4. 用户访谈方案尚未执行，不能声称用户愿意授权数据、执行建议或持续使用。
5. 小样本测试只能提供早期方向，不足以证明长期留存、付费意愿或规模化 ROI。
6. 反事实省钱基线易受天气、季节、设备变化与用户行为干扰，需真实数据实验。
7. 应急续航预测关系安全，应展示区间、更新时间与降级策略，而非单点数字。
8. 语音的实际使用频率尚未验证，不能用命令表完整程度证明需求强度。

## 8. 可复现流程

另一位产品经理可按以下步骤复做本项目，不要求逐字相同的 AI 文本：

1. **固定输入**：记录目标市场、设备范围、预算口径与不能假设的能力；输入数字统一标 F2。
2. **最小框架**：仅输出协同组合、价值量化与语音必要性的框架，并列出每个判断依赖的前提。
3. **场景闭环**：对每个场景补痛点、AI 价值、商业价值、差异化、指标与异常分支。
4. **IA 与流程**：按 P0/P1/P2 排序功能，再设计首次设置、日常优化、停电应急的端到端流程。
5. **量化模型**：以反事实基线计算净节省，拆分收益去重，明确已验证 / 估算 / 潜力口径。
6. **事实核验**：每个关键事实保存标题、链接、访问日期与它支持的具体主张。
7. **红队质疑**：逐项追问，成立即修正。
8. **先证伪再投入**：可交互原型 + 脱敏真实数据 + 人工陪跑 → 验证授权 / 执行 / 复访 → 内嵌 MVP → 对照实验。
9. **整合**：只纳入「采用 / 修正后采用」的内容，并设置已核验事实、待验证假设、停止条件三张清单。
